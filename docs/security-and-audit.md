# امنیت، ممیزی و آمادگی عملیاتی

این سند جمع‌بندی کنترل‌های امنیتی و ممیزی است: چه چیزی محافظت می‌شود،
چطور ممیزی می‌شود، و اپراتور چطور باید واکنش نشان دهد.

## ۱. احراز هویت

| کنترل | وضعیت | کجا |
|---|---|---|
| ورود با کد شرکت + ایمیل + رمز | فعال | `/auth/login` |
| هش رمز با bcrypt | فعال | `app/core/security.py` |
| توکن JWT با انقضای قابل تنظیم | فعال | `ACCESS_TOKEN_EXPIRE_MINUTES` |
| ورود دومرحله‌ای TOTP | فعال | `verify_totp` در `routes/org.py` |
| خروج همهٔ نشست‌ها | فعال | `POST /auth/logout-all` |

کد TOTP در صفحهٔ تنظیمات **پنهان است** تا کاربر روی «نمایش رمز» کلیک کند؛
در متن صفحه و در لاگ‌ها هرگز ظاهر نمی‌شود.

## ۲. مجوزدهی

سه لایه، هر سه باید بگذرند:

1. **نقش** — کاربر یک نقش دارد (`role_id`)، نقش مجموعه‌ای از مجوزهاست.
2. **دامنه** — هر مجوز یک `scope` دارد: `own`، `team`، `branch` یا `org`.
   فیلتر دامنه در `app/core/scope.py` اعمال می‌شود، نه در هر route جدا.
3. **شعبه** — کاربران شعبه‌محور با `branch_id` به دادهٔ همان شعبه محدودند.

نمونهٔ درست — چک مجوز قبل از هر کار حساس:

```python
try:
    require_permission(ctx.permissions, PermissionCode.ORG_ADMIN)
except AuthorizationError as e:
    raise handle_authz(e) from e
```

پاک‌سازی حریم خصوصی مشتری (`POST /customers/{id}/erase`) فقط با `org.admin`
انجام می‌شود و لاگ ممیزی می‌نویسد.

## ۳. جداسازی خود-تأییدی

درخواست‌دهنده **نمی‌تواند** خودش را در زنجیرهٔ تأیید بگذارد:

```python
# app/services/enterprise_ops.py — request_approval
if requester_id in approver_ids:
    raise ValueError("درخواست‌دهنده نمی‌تواند تأییدکنندهٔ درخواست خودش باشد")
```

این قاعده در دو مسیر حیاتی است:

- API وب (`POST /approvals`) — خطای ۴۰۰ می‌دهد.
- ابزارهای حساس AI (`app/ai/tools.py`) — اگر کاربر مدیر نداشته باشد، تأیید به
  ادمین سازمان می‌رود؛ اگر هیچ تأییدکننده‌ای نباشد، ابزار **اجرا نمی‌شود**.

بیماری که این قاعده بست: `ai/tools.py` قبلاً برای کاربر بدون مدیر،
خودِ او را تأییدکننده می‌گذاشت و حاکمیت AI بی‌اثر می‌شد.

## ۴. زنجیرهٔ هش لاگ ممیزی

`audit_logs` در سطح API فقط-افزودنی است، ولی دسترسی مستقیم به دیتابیس
می‌توانست سطرها را تغییر یا حذف کند. از مهاجرت `0011` هر سطر دو ستون دارد:

- `prev_hash` — هش سطر قبلی در همان سازمان
- `row_hash` — هش محتوای همین سطر + `prev_hash`

زنجیره به‌ازای هر سازمان جداست. حذف یا ویرایش هر سطری، هش همهٔ سطرهای
بعدی را بی‌اعتبار می‌کند.

ترتیب زنجیره با ستون `chain_seq` تثبیت شده، نه `created_at` — چون دقت
`created_at` در SQLite پایین است و چند سطر پشت‌سرهم می‌توانند زمان یکسان
بگیرند.

نوشتن زیر قفل انجام می‌شود: در Postgres با `FOR UPDATE` روی سطر آخر، و
در SQLite (که `FOR UPDATE` را پشتیبانی نمی‌کند) با قفل درون‌پروسه‌ای به‌ازای
هر سازمان. بدون این قفل، دو تراکنش هم‌زمان هر دو `chain_seq` یکسان می‌گرفتند.

### راستی‌آزمایی

```bash
cd backend
uv run python -m scripts.verify_audit_chain           # همهٔ سازمان‌ها
uv run python -m scripts.verify_audit_chain --org autoco
uv run python -m scripts.verify_audit_chain --json    # برای مانیتورینگ
```

خروجی سالم:

```
[سالم] autoco: 412 سطر

1 سازمان، 412 سطر بررسی شد — 0 مشکل
```

خروجی دستکاری:

```
[شکسته] autoco: 412 سطر
        نقطهٔ شکست: customer.erased — محتوای سطر تغییر کرده

1 سازمان، 412 سطر بررسی شد — 1 مشکل
```

کد خروج `1` است اگر هر زنجیره‌ای شکسته باشد — پس مستقیم به مانیتورینگ
داده می‌شود. این مرحله در CI هم اجرا می‌شود.

## ۵. حفاظت از داده

| کنترل | توضیح |
|---|---|
| هش نگهداری | `archived_at` — حذف فیزیکی انجام نمی‌شود |
| پاک‌سازی مشتری | `erase` نام/تلفن/ایمیل را خالی می‌کند، رکورد و ممیزی می‌ماند |
| رمزها در لاگ | هر `*_SECRET*`/`*TOKEN*`/`*PASSWORD*` با regex به `***` تبدیل می‌شود |
| رمزهای استقرار | `deploy/make-secrets.sh` پنج رمز تصادفی متمایز می‌سازد |
| compose بدون رمز | `docker-compose.prod.yml` با `${VAR:?}` fail-fast است |

## ۶. سربار‌های HTTP

- `app/core/ratelimit.py` — محدودیت نرخ بر اساس کاربر و مسیر.
- `assert_production_safe` — در محیط production، نبودِ رمز یا `APP_ENV`
  اشتباه، استارت را متوقف می‌کند.
- `app/core/metrics.py` — `cm_http_requests_total` و هیستوگرام تأخیر روی `/metrics`.

## ۷. هدرهای امنیتی وب

`deploy/nginx.conf` این هدرها را می‌فرستد:

`Content-Security-Policy` (با `frame-ancestors 'none'` و `object-src 'none'`)،
`X-Content-Type-Options`، `X-Frame-Options`، `Referrer-Policy`،
`Permissions-Policy`، `Strict-Transport-Security` و `Cross-Origin-Opener-Policy`.

اعتبارسنجی در CI با `nginx -t` انجام می‌شود.

## ۸. واکنش به حادثه

اگر `verify_audit_chain` شکست گزارش کرد:

1. **توقف نکنید** — سرویس با زنجیرهٔ شکسته کار می‌کند، فقط قابل اثبات نیست.
2. سطر شکسته را از پیام خطا بردارید (`broken_at` و `detail`).
3. اگر سطر **حذف** شده: `chain_seq` از جایی می‌پرد — `detail` می‌گوید «حذف یا درج».
4. اگر سطر **ویرایش** شده: `detail` می‌گوید «محتوای سطر تغییر کرده».
5. از پشتیبان (`deploy/backup.sh`) نسخهٔ قبل از حادثه را برگردانید.
6. دسترسی دیتابیس را بررسی کنید: `POSTGRES_PASSWORD` و `MINIO_ROOT_PASSWORD`.

## ۹. آنچه پوشش داده نمی‌شود

صادقانه، برای اینکه بدانید مرز کجاست:

- **رمزنگاری در حال انتقال** — TLS بین کلاینت و nginx دارد، ولی بین nginx و
  PostgreSQL در `docker-compose.prod.yml` شبکهٔ داخلی است. برای دادهٔ حساس
  در شبکهٔ نامطمئن، TLS بین سرویس‌ها لازم است.
- **رمزنگاری در حال ذخیره** — دیسک رمزنگاری‌نشده. به کلید مدیریت بستگی دارد.
- **WAF / محدودیت DDoS** — در برابر حملهٔ لایهٔ ۷ در nginx محافظتی نیست.
- **حسابرسی مستقل** — ممیزی داخلی است، نه ممیزی بیرونی. برای الزام قانونی،
  لاگ ممیزی باید به سامانهٔ WORM سازمانی هم برود.
- **حریم خصوصی داده** — `erase` مشتری را پاک می‌کند ولی پیام‌های گفتگو و
  تاریخچهٔ تأیید نگه داشته می‌شوند (برای ممیزی لازم است).
