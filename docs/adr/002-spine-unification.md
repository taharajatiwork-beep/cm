# ADR 002: یکپارچه‌سازی ستون فقرات (Work / Request / Project)

**وضعیت:** پذیرفته — فاز B (read-model `spine`) در حال اجرا  
**تاریخ:** ۱۴۰۵/۰۷/۲۱  
**مرجع:** [unification-plan.md](../unification-plan.md)

## مسئله

امروز چهار لایه هم‌پوشان داریم:

- **Work Item** + **Task** + **Case** (فروش و پیگیری)
- **WorkRequest** + **WorkProject** + **PmCampaign** (مارکتینگ)
- گفتگو و پیام به چند موجودیت وصل می‌شوند (`project_id`, `request_id`, `work_item_id`, `campaign_id`, `pm_campaign_id`)

کاربر «یک کار» می‌بیند؛ دیتابیس چند جدول دارد. بدون مرحله‌بندی، migration و UI هر دو می‌شکنند.

## گزینه‌ها

1. **ادغام فیزیکی فوری** — یک جدول `work_spine` و حذف جداول قدیمی. ریسک بالا، downtime داده.
2. **مدل مفهومی واحد + جداول فعلی (انتخاب پیشنهادی)** — یک نوع منطقی `SpineNode` با `kind` و FKهای nullable؛ API و UI تدریجی هم‌نام شوند؛ جداول legacy تا فاز N readonly می‌مانند.
3. **فقط UI** — بدون تغییر schema؛ کافی نیست برای گزارش و گفتگوی واحد.

## تصمیم پیشنهادی (گزینه ۲)

### مدل مفهومی

| مفهوم واحد | نقش | جداول فعلی |
|------------|-----|------------|
| **نیاز (Need)** | خواستهٔ ورودی | `work_request`, بخشی از `case` |
| **ظرف (Container)** | اجرای تیم‌محور | `work_project`, `work_item` (تا ادغام تدریجی) |
| **اقدام (Action)** | واحد انجام | `task` |
| **رصد (Track)** | پیگیری مشتری/SLA | `case` |
| **اجرای تبلیغ** | فقط `kind=پرفورمنس` | `pm_campaign` |

**کمپین پرفورمنس** فقط به پروژهٔ با `kind=پرفورمنس` (یا معادل) وصل می‌شود. **طراحی** و **فیلم‌برداری**: بدون `pm_campaign`؛ وظیفه + «اعمال قالب» (`apply-template`) + `design_deliverable` / `shoot`.

### فازهای پیاده‌سازی (بعد از تأیید)

| فاز | محدوده | ریسک |
|-----|--------|------|
| A | واژه‌نامه UI + گزارش‌ها با نام درست | کم |
| B | API read-model واحد «خط زمین» برای پروژه/درخواست (بدون حذف جدول) | کم |
| C | یک فهرست «کارهای من» از union task + نقش participant | متوسط |
| D | ادغام نمایشی Work Item → Project برای فروش (لینک، نه migrate داده) | متوسط |
| E | migration دادهٔ Work Itemهای قدیمی به Project (اختیاری، per-org) | بالا |

هر فاز: migration جدا، تست regression، بدون شکستن `/perf/*`, `/requests`, `/pricing`.

## خطوط قرمز

- تأیید خودکار میزیتو، پرداخت واقعی، ارسال SMS، تبدیل درخواست→پروژه بدون کاربر: خارج از scope این ADR.

- تست `test_unification.py` و IDOR سبز بمانند.
