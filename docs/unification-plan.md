# طرح یکپارچه‌سازی — تصمیم‌های ثبت‌شده

حداکثر دو صفحه. این تصمیم‌ها با کد فعلی سازگار شده‌اند و سؤال باز ندارند.

## ۱. فرض‌هایی که با کد نمی‌خواند

- Work Item و Project یکی نیستند. کار مشترک هاب فروش است؛ پروژه ظرف مارکتینگ. وظیفه به هر کدام جدا وصل می‌شود و «کارهای من» هر دو را نشان می‌دهد.
- «کمپین» ارتباطات (`campaigns`) با کمپین پرفورمنس (`pm_campaign`) فرق دارد. فقط برچسب رابط به «موضوع گفتگو» عوض می‌شود.
- `manager_ok` در وضعیت هزینه هست ولی تأیید مالی امروز یک‌ضرب به `recorded` می‌رود. این رفتار برای `/perf/money` بدون پروژه می‌ماند. اگر هزینه `project_id` یا `request_id` داشته باشد، اول اقدام `manager` لازم است.
- scope نقش مدیر مارکتینگ در seed برابر `team` است. `team_tree` فقط با `request.triage` یا `request.manage` یا scope از `department` به بالا داده می‌شود، روی تیم کاربر و فرزندان `parent_team_id`. گزارش نقش پرفورمنس حداکثر `team` است؛ مسیرهای `/perf/*` دست نمی‌خورند.
- سرویس هزینه در `app/perf/services/payments.py` می‌ماند (شارژ پنل همان‌جا است). هسته آن را import نمی‌کند. ستون‌های پروژه روی همان جدول اضافه می‌شوند. این انحراف از «انتقال کلاس» است تا ده‌ها import نشکند.
- گام بعدی کمپین از `queue.py` در فرانت با دادهٔ `/perf/home` نشان داده می‌شود تا `app.requests` مجبور به import پرفورمنس نشود.
- مایگریشن sqlite ستون Uuid را بدون FOREIGN KEY در ALTER اضافه می‌کند (مثل 0023).

## ۲. مدل‌ها

تعمیم: `tasks` (`project_id`, `request_id`)، `conversations` (`project_id`, `request_id`)، `messages` (`task_id`, `perf_campaign_id`)، `work_project` (`due_date`, `planned_budget`, `lead_user_id`)، `pm_payment_request` (`project_id`, `request_id`, `team_id`)، `post_slots` (`project_id`, `request_id`).

جدید: `work_attachment`، `design_deliverable`، `shoot`.

## ۳. مایگریشن‌ها

- `0024_work_spine` — وظیفه، گفتگو، پیام، پروژه، پیوست
- `0025_expense_link` — اتصال هزینه و مجوزهای expense برای نقش‌های `price.write`
- `0026_work_types` — اسلات قیمت، طراحی، فیلم‌برداری

## ۴. ریسک عقب‌رو

مسیرهای `/perf/*`، `/requests`، `/projects`، `/pricing` و `/reports/kpis` همان قرارداد را دارند. فیلدهای جدید nullable هستند. هزینهٔ قدیمی بدون پروژه یک‌مرحله‌ای می‌ماند.

## ۵. نقشهٔ مفاهیم

| مفهوم | مرز |
|---|---|
| درخواست | خواستهٔ مدیر. یا پروژه می‌شود یا وظیفهٔ عملیاتی. خودش اجرا نیست. |
| پروژه | ظرف تیم‌محور مارکتینگ. پیشرفت از وظایف محاسبه می‌شود. |
| کار مشترک | همکاری فروش/شعبه. به پروژه تبدیل نمی‌شود. |
| وظیفه | واحد اجرا. به کار مشترک، پرونده، پروژه یا درخواست وصل است، نه به هر چهار تا به‌اجبار. |
| پیگیری | رصد موضوع مشتری. جدا از درخواست کار. |
| موضوع گفتگو | کمپین جدول `campaigns` در پیام‌ها. |
| کمپین پرفورمنس | اجرای تبلیغ. با `project_id` به پروژه وصل است. گام بعدی‌اش ذخیره نمی‌شود. |
| گفتگو | یک رشته برای هر پروژه یا درخواست عملیاتی. وظیفه رشتهٔ جدا ندارد؛ پیام می‌تواند به وظیفه ارجاع بدهد. |
